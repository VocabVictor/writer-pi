# 缓存失效调研笔记（事实素材）

## 问题背景

- 我们的服务用 Redis 做读缓存，QPS 高峰约 1.2 万，命中率长期在 96% 左右。
- 每次价格配置变更上线后，几分钟内会出现一批旧价格订单，客服投诉集中在这些订单上。
- 根因不是缓存没写，而是失效通知丢了：变更服务发 Redis pub/sub，订阅方重启窗口内的消息全部丢失。

## 常见失效方式与问题

- 主动删除（写库后 DEL 缓存键）：简单，但跨服务时谁负责删不清晰；我们曾有 3 个服务都认为自己负责删同一个键，结果谁都没删。
- TTL 兜底：设置 5 分钟过期，作为丢失通知的最后防线。纯 TTL 会让旧数据最长存活一个 TTL 周期。
- 版本号键：缓存键里带配置版本（price:v37:sku123），切换版本后旧键自然失活，读方需要先拿到当前版本号，多一次查询。
- 延迟双删：写库前后各删一次，中间 sleep 数百毫秒，用来覆盖"读请求在写库前读到旧值又回写缓存"的并发窗口。有人认为这是土办法，但它不依赖基础设施语义。

## 测量数据

- pub/sub 消息丢失率在发布方重启时接近 100%，平时为 0； Quarterly 一次的部署频率意味着每月至少一次丢失窗口。
- 引入"先取版本号再读缓存"后，命中率从 96% 降到 91%，读路径 P99 从 8ms 升到 11ms，但旧价格订单投诉降为 0。

## 结论倾向

- 失效正确性不能依赖单次通知必达；要有 TTL 或版本号这类不依赖通知的兜底。
- 代价要量化：多一次查询带来的延迟上升，和旧数据造成的业务损失，放在一张表里比。
